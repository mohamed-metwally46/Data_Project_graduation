# Proposed listing contract and isolated fixture workflow

The proposed listing bundle schema has a fixture envelope and a future intermediate population envelope. It contains product references, listings, registry entries and planning mappings. Each listing carries linked supplier, supplier role and supplier-product association UUIDs, a canonical product UUID and source product code, market, variant, display code, English fictional presentation, authoritative status, exact Decimal commercial terms, and source and planning provenance. Backend compatibility requires separate mapping and review. [Canonical listing schema v1.0.0](../schemas/listing_stage.proposed.schema.json)

Under the proposed UUID v5 specification, derive entity namespaces under the existing population namespace using the entity tokens `product` and `listing`. A product key is the ordered array `["globiq-trade-reference-2024-v1", "<normalized source code>"]`. The context identifies the Globiq source catalog without assigning an official revision. Keep existing semantics under this context across releases. Change the version and document migration if the same code acquires different semantics. Preserve six-digit codes as strings and preserve literal `9999AA`.

The listing key is `["<supplier company UUID>", "<canonical product UUID>", "default"]`. Variants use lowercase ASCII letters, digits and hyphens with a leading letter and a maximum of 40 characters. The external key is encoded as compact UTF-8 JSON with NFC strings in the existing versioned key envelope. Initial display codes use `LST-NNNNNN` in sorted original planning-reference order. Later revisions use the persisted registry. Retirement retains UUID, key and display reservations. Reactivation requires explicit continuity review of the same listing. Mutable terms, presentation and status never enter the identity key.

Catalog visibility derives from status. Active and out-of-stock listings can be shown, while inactive listings are excluded. Only active listings are considered for matching, subject to request-specific checks for product, unit, increment, MOQ, stock, maximum order and baseline trade evidence. Stock represents a synthetic scenario value. Display the quoted price with currency and basis, identify the units using the registry labels and mark the catalog as synthetic.

The fixture CLI exercises canonical serialization and an independent validator. Fixtures use a separate root and population and remain outside the data directory. The production command is gated. [Identifier and authorization package](SM04_LISTING_STAGE_AUTHORIZATION.md)

## Remediation status

The v1.1 production-shaped contract requires suitable products before catalog or matching checks and uses source-scoped product ID plus explicit commercial specification. The future validator entry is `validate_serialized` in `listing_population_validation.py`, and the publication boundary invokes the same validation before rejecting unapproved execution. The historical fixture contract remains available for compatibility. The only v1.1 data exercised is isolated fixture data. [Remediation evidence](../reports/sm04a_remediation_report.json)
